# Repository guidance

- This repository owns the execution entry, generated task prompts, the execution ledger and the planning tool; formal documentation is English. ArcForges-Design-B owns the authoritative delivery model and graph (`docs/planning/delivery/`).
- There is no single Current task. Any number of workers may execute different ready tasks concurrently; a task is owned only through an atomic `claims/<task-id>` branch in this repository. Follow [arcforges-implementation.md](arcforges-implementation.md) and [execution-policy.md](execution-policy.md).
- The user's latest instructions determine whether to start, continue or stop; documents are execution guidance, not independent authorization or mandatory stopping rules.
- `list.md`, `tasks/*.md` and the Design delivery views are generated by `tools/delivery.py` from the Design graph; never edit them by hand. Planning changes edit the Design graph, then run `python tools/delivery.py generate --design <Design-B checkout>` and `check`.
- The remote/web execution-prompt variants (`arcforges-implementation-remote.md`, `list-remote.md`) are excluded from the current execution model, are not maintained and must not be used as execution authority. This does not exclude the Web product.
- Work in retained Git worktrees; append to related open PRs and leave unrelated PRs alone. Ledger records are one file per task under `ledger/tasks/`.
- Follow Design P2-017 as amended by P2-018. Never prescribe macOS CI, hosted runtime/device/browser/live-service/inference/installed-consumer tests or routine public-download/hash/install revalidation.
- Preserve necessary Windows/Linux build/offline/static/security and signing/licence/lock checks. Runtime checks are scoped local opt-in using existing tools, once per relevant change; no toolchain reinstall.
- Serialize CPU-heavy local builds per workstation and avoid hidden Git-hook builds.
- No explicit proxy or wsl.exe wrapper. Stop and identify a failed network operation instead of retrying or changing network settings.
- Review every PR. Documentation repositories with no CI merge directly after review; code repositories run existing applicable CI even for documentation-only changes and merge only after all retained latest-head checks succeed. Do not skip checks or weaken branch protection for documentation changes. Post-merge: commit/job status and primary fast-forward only. Keep branches/worktrees.
